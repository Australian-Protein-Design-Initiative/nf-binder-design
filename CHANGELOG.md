## [Unreleased]

### Fixed
- Structures were discarded whole when an engine wrote a placeholder for an atom it did not model. RFdiffusion3 and ProteinMPNN give the terminal `OXT` NaN coordinates, which the PDB writer rejects, so EnGens clustering skipped the structure and refold interface scoring (`bin/structure_to_pdb.py`) failed its task. Only the unmodelled atoms are dropped now, with a warning naming them; the residue keeps its remaining atoms, and nothing in the backbone comparison used `OXT` anyway.
- EnGens clustering silently dropped every prediction from engines whose mmCIF writer omits `_atom_site.occupancy`, notably OpenFold3 and RFdiffusion3, so a `--method fold` run naming them clustered only the other engines' models. The CIF-to-PDB conversion now goes through biotite, which the report already uses for its 3Di alphabet, rather than `Bio.PDB.MMCIFParser`, which requires that column. The report also prints structures read per engine and raises a warning listing any input it could not read, so a whole engine going missing is visible rather than buried in a log.
- Every method published its fold and refold outputs under `results/rfd/refold` on Nextflow 26, which evaluates the `params` defaults of every included script, so the first workflow `main.nf` includes decided the directory for all of them. `--refold_publish_dir` and `--fold_publish_dir` are now derived from `--method` in `nextflow.config`, so `--method fold` publishes to `results/fold` again. `--method bc2` and `--method boltzgen` refolds move from `results/refold` to `results/<method>/refold`, matching the other design workflows.
- `--method bc2` dual-GPU examples (`pdl1-bc2`, `pdl1-bc2-mini`, `bindcraft2-vhh`) ran one batch at a time. `BINDCRAFT2` reserved 32 GB, so a second task did not fit in host RAM and the other GPU stayed idle.

### Added
- `examples/pdl1-rfd4-proteina/run-local-simple-dual-gpu.sh`: the params-mode PD-L1 RFD4-Proteina run spread across two local GPUs.
- `--method bc2` (alias `bindcraft2`): parallel [BindCraft2](https://github.com/PacesaLab/BindCraft2) binder design. Takes either a campaign settings JSON (`--bc2_config`, with referenced target structures and scaffolds staged automatically) or flat params shared with `--method bindcraft`. Runs a fixed trajectory budget (`--bc2_n_traj`, `--bc2_batch_size`) with a distinct `campaign_seed` per batch, then gathers the batches with `bindcraft campaign_output` into one ranked summary plus an HTML report. Binder modalities via `--bc2_modality` (VHH, scFv, Fab, cyclic peptide, ...), composable design properties via `--bc2_humanize`, `--bc2_protease_stable` and friends, and every other BindCraft2 setting via `--bc2_set 'KEY=VALUE;KEY=VALUE'`. `--hotspot_subsample` draws a different subset of each target's hotspots per batch, in both input modes, seeded so the run still reproduces. `--do_foldseek` runs a FoldSeek structural novelty search over the ranked designs, searching only the binder chains.
- `--complex_structures` for `--method fold_pulldown`: supply target-binder complexes instead of a binder FASTA. The binder chain of each is folded against every target as usual, and the complex is then the reference its predictions are compared against, giving `target_aligned_binder_rmsd_all`, TM-score, DockQ and interface quality in `complex_rmsd.tsv` - one comparison per (target, engine, sample), all against the one complex that binder came from. This answers whether a binder still sits the same way against a different, longer or variant target. `--binder_chains` names the binder chain(s); several means several binder records per complex, named `<complex>_<chain>`. `--target_chains` chooses the superposition reference, defaulting to whichever chain is not a binder chain, so a two-chain complex needs only `--binder_chains`; `auto` resolves it per complex by matching against the `--targets` records, for mixed-source complexes with inconsistent chain naming, and logs the chain it chose. `--targets` is optional here: without it the targets are read back out of the complexes' own target chains and deduplicated by sequence, and a set holding more than one distinct target stops the run rather than folding every binder against every target. A multi-chain target is not supported, since a pulldown folds two-chain pairs and there would be nothing to superimpose a second target chain onto. `complex_rmsd.tsv` carries a `target` column, which is what tells one binder's rows apart when it was folded against several.
- Refold scoring reports DockQ. `combined_scores.tsv` and `refold_sample_scores.tsv` gain `<tool>_target_aligned_binder_dockq`, with its `_dockq_fnat`, `_dockq_fnonnat`, `_dockq_irmsd`, `_dockq_lrmsd`, `_interface_lddt` and `_clash_count` companions, measuring the refolded complex against the design pose. On by default (`--refold_dockq false` to drop them): the comparison reads structures that have already been written and needs no GPU, so it adds very little to a refold that has just paid for the folding. Only the target-aligned comparison gets them, since DockQ needs a receptor and a ligand and the whole-complex comparison puts both chains on both sides. Needs `nf-binder-design-utils:0.1.8`.
- `bin/rmsd4all.py --dockq`: DockQ, its `fnat` / `fnonnat` / `iRMSD` / `LRMSD` components, interface lDDT and a clash count for a reference-versus-pose comparison, computed with [peppr](https://peppr.proximabio.com). The superimposition chains are the receptor and the scored chains the ligand, so a target-aligned binder comparison already names both. Agrees with the reference DockQ implementation to three decimal places on `fnat`, `iRMSD` and `LRMSD`; unlike it, the receptor/ligand roles follow the chains given rather than chain size, which only changes `LRMSD` (and so DockQ) when the ligand is the larger chain. Residues are paired by sequence alignment and each pair keeps the atoms both structures carry, so a backbone-only design scores against an all-atom prediction on the backbone. Not yet exposed as a workflow parameter, and the `nf-binder-design-utils` container needs `peppr` before the Nextflow modules can pass `--dockq`.
- `--method rfd4_proteina`: binder design with [RFD4-Proteina](https://github.com/RosettaCommons/RFD4-Proteina). The model co-designs sequence and structure, so there is no inverse-folding step between generation and scoring. An RFD4-Proteina condition spec (`--rfd4_config`, YAML or JSON) is the default interface and gives access to the full conditioning vocabulary; `--input_pdb` with `--contigs` and `--hotspot_res` generates one using the upstream default recipe for protein binders, naming the designed segment `BINDER` (or keeping the name `--contigs` gives it, as in `"BINDER: 50-120, /0, A17-131"`) and excluding cysteines from it (`C_SEQ_PROB_CYS`); the generated spec is published to `rfd4_proteina/input/config/`, so it can be copied with that condition dropped to allow them. Each batch's raw `rfd4-generate` run directory, holding the inference metrics and the inline refolds, is published to `rfd4_proteina/batches/batch<n>/`, and the inline metrics are merged into `combined_scores.tsv` prefixed `rfd4_` (`rfd4_oracle_ppi_overall_iptm`, `rfd4_hotspot_obedience_hotspot_obedience`, `rfd4_ppi_pass`, ...). Designs are split across tasks by `--rfd4_designs_per_task`, each with its own seed. Supports structural filters (`--rfd4_filters`), Boltz-2 refold scoring (`--refold_with boltz`), FoldSeek search (`--do_foldseek`), partial diffusion and inverse folding. Runs in the `rfd4-proteina:0.0.3-6306a21_nv-cuda13` container, which is published for both amd64 and arm64 (`..._arm64`). On an arm64 host, add `-c conf/platforms/arm64.config` so the other steps use arm64 images too. Inline RFD4-Proteina metrics run by default (`--rfd4_metrics_tags ppi_refolding,hotspot_conditioning`, `false` to disable) and `--rfd4_recycle_strategy` defaults to `medium/front_loaded`; both can be overridden. Adding `apo_refolding` to the tag list also refolds the designed binder alone, reporting its confidences (`rfd4_oracle_apo_apo_overall_plddt`) and its backbone RMSD against the refolded complex (`rfd4_refolded_apo_holo_rmsd_apo_rmsd`), which says whether a binder holds its designed fold without its target.
- `--refold_with` takes a list of engines: refold scoring is one path now, whichever predictor does the folding. Each design's binder sequence is folded against its target with every engine named - `af2`, `af2_mono`, `boltz`, `rf3`, `protenix`, `af3`, `openfold3`, `chai1`, `esmfold2`, `esmfold2_fast` - and every engine gives the same columns in `combined_scores.tsv`, prefixed with its name: confidence (`<tool>_iptm_max`, `<tool>_ipsae_max`, `<tool>_plddt_max`, ...), RMSD against the design (`<tool>_target_aligned_binder_rmsd_all`, `<tool>_complex_rmsd_all`), the binder folded on its own (`<tool>_monomer_vs_design_rmsd_all`, `<tool>_monomer_vs_complex_rmsd_all`) and BindCraft interface metrics (`<tool>_interface_dG`, ...). A cross-engine `consensus_z` ranks designs when more than one engine is named. New parameters: `--refold_metrics`, `--refold_structure_stat`, `--refold_binder_monomer`, `--refold_monomer_single_sequence`, `--refold_interface_scoring`. The new `REFOLD` subworkflow takes designs as `tuple(meta, structure, scores)` and holds nothing design-method-specific, so every design workflow uses it: `rfd`, `rfd_partial`, `rfd3`, `rfd4_proteina`, `bindcraft` and `germinal`.
- `--refold_target_fasta`: refold the selected designs against a target other than the one they were built against, given as a FASTA of exactly one record. Without it the refold target is the target chain read back out of the design structures, so a binder designed against a truncated construct is only ever checked against that same truncated construct; this is how it is checked against the full-length protein instead, which is a different and harder question than the one the design run answered. One record only, because every binder is folded against every target and one row per design in `refold_scores.tsv` depends on there being a single target. The designs' own target is still read, and the run warns when the supplied sequence does not contain it - the usual sign that `--refold_target_chain` or the FASTA is not what the run assumed. Pair it with `--templates` for that target's structure and `--target_msa` or `--create_target_msa` for its MSA. With a longer target the refolded complex and the design are no longer the same molecule, so `<tool>_complex_rmsd_all` and `<tool>_complex_tm_score_all` come back as `nan`; the structurally aligned `_pruned` variants and the target-aligned binder RMSD, which is the pose metric, are unaffected.
- `--target_msa` for `--method fold_pulldown` and for refolding: an A3M for the target built elsewhere, used instead of searching for one. Its first record must be the target sequence being folded. One file describes one target, so a pulldown over several stops rather than handing them all the same alignment, and it cannot be combined with `--create_target_msa`. This is the replacement for the old `--full_refold_alignment` / `--refold_alignment`.
- `--method fold`: multi-method structure folding for monomer and multimer/complex FASTA inputs with AF2, `af2_mono` (AF2 monomer weights on a chain-broken complex), Boltz-2, RosettaFold3, Protenix, AlphaFold3, OpenFold3, Chai-1, ESMFold2 and ESMFold2-Fast (`esmfold2_fast`). Shared MSAs (jackhmmer/HHblits or ColabFold, taxonomy-paired per engine for multimers), optional MSA subsampling, a per-structure score table (ipTM, pLDDT, ipSAE, pDockQ, LIS, ...) and EnGens clustering. AlphaFold3 weights are not bundled: download them under DeepMind's terms with `models/download_af3_weights.sh`, or point `--af3_model_dir` at them. ESMFold2 weights ship in its containers; `esmfold2_fast` always folds from sequence alone, and `--esmfold2_single_sequence` runs the full model MSA-free too. Also `engens.nf` for clustering an existing `.cif`/`.pdb` folder or glob.
- `--method fold_pulldown`: target × binder pulldown across the same engines, with per-structure scores, an aggregate summary (within-tool z-scores and a cross-engine `consensus_z`) and a Quarto report. MSA cost is O(targets + binders) rather than O(targets × binders), and input ids are validated up front. Defaults to 5 structures per complex per engine (`--n_predictions`), with AF2 keeping all five models from its single run (`--af2_keep_models all`).
- `--templates` for `--method fold` / `fold_pulldown`: known structures (`.pdb`/`.cif`, single chains or whole complexes) are matched to the chains being folded by sequence alignment, with no mapping file, and passed as per-chain templates to every engine except ESMFold2. Match cutoffs are `--template_min_identity`, `--template_min_coverage`, `--template_min_aligned` and `--template_max_per_chain`. fold_pulldown templates the target only unless `--binder_templates`, and by default holds Boltz's templated chains near their template (`--boltz_template_force`, 1.0 Å).
- `--boltz_refold_batch_size`: fold several designs per Boltz refold task to amortise Boltz's per-invocation startup cost (default 1).
- AlphaFold3 can be run the way [Germinal](https://github.com/SantiagoMille/germinal) runs it, so an AF3 refold of Germinal designs is comparable to the scores that run produced. `--af3_paired_msa false` emits `"pairedMsa": ""` for every chain (no cross-chain pairing); `--af3_templates search` omits the `templates` key so **AF3's own data pipeline searches `pdb_seqres`/`mmcif_files` for templates on every chain**, which `--af3_run_data_pipeline true` and `--af3_db_dir` (the ~630 GB AF3 database set) enable. `--af3_seeds` also takes a comma list, putting every seed in one job's `modelSeeds`; the seed list is then the replication, so the `--n_predictions` fan-out is suppressed and a run produces `n_seeds × --af3_batch_size` structures per complex. `-profile af3_germinal_parity` packages the whole combination with Germinal's target-only MSA mode and 5×5 sampling. Defaults are unchanged — without these AF3 still runs inference-only with a paired MSA and no templates.
- `conf/platforms/arm64.config`: run on arm64 / aarch64 workstations (eg NVIDIA DGX Spark GB10) by pointing the amd64-only images at their arm64 builds - `nf-binder-design-utils:0.1.8-arm64`, `boltz:v2.2.1-2_nv-cuda13-arm64`, `foldseek:10-941cd33-arm64`, `esmfold2:3.4.1.post1_nv-cuda13-arm64_{fast,full}_weights`, `rc-foundry:0.2.0_arm64-weights` (RF3), `bindcraft:nv-cuda13-arm64` and `protenix:2026-09-21_85767b8_nv-cuda13-arm64_weights`. Covers the RFD4-Proteina design path and its scoring, with `boltz`, `esmfold2`, `esmfold2_fast`, `rf3` and `protenix` available as refold engines; AF2, AF3, OpenFold3 and Chai-1 have no arm64 image yet. Two of those images need a GB10-specific build rather than only an architecture swap. RF3 uses the `-ngc2606` tag rather than the plain `0.2.0_arm64-weights` one: the latter is built on CUDA 12.8, whose nvrtc cannot target `sm_121`, so on a GB10 it fails with `nvrtc: error: invalid value for --gpu-architecture (-arch)` when PyTorch's jiterator compiles `erfinv`. Protenix compiles its fused layer-norm extension at image build time for `sm_70` to `sm_100` only, so inference died at the first layer-norm call with `no kernel image is available for execution on the device`; the arm64 image adds `sm_120` and `sm_121` and rebuilds it. Protenix also needs `HOME` set to a writable path when run as the host uid under Docker, which the config does, since it caches under `$HOME/.cache` and an unset `HOME` resolves to `/`. Use it alongside a runtime config, eg `-c conf/platforms/arm64.config -c nextflow.docker.config`. It also sets `--gpu_devices all` and `--gpu_slots_per_device 1`: without `--gpu_devices` the GPU lock never engages and fold tasks run concurrently on the one device, which on a GB10 - where the 128 GB is shared between host and GPU - is enough to run it out of memory.
- `refold/refold_sample_scores.tsv`: one row per refolded sample, keyed by `id`, `tool`, `batch` and `model`, carrying that sample's own confidence, RMSD and interface scores with nothing reduced. `combined_scores.tsv` is one row per design, so every number in it is already a statistic over the samples; this table keeps the values those statistics were computed from, so min, max, mean, median or standard deviation over the samples can be worked out afterwards.
- `--refold_structure_stat` (default `selected`): how several samples per design reduce to one value in the RMSD **and** interface columns of `combined_scores.tsv`. They now come from a single sample, the one the confidence ranking picks as best (by `--consensus_metric`, ipSAE), rather than a statistic per metric. The structural metrics all describe one set of coordinates, so taking the lowest RMSD and the lowest `interface_dG` independently gives a row that no predicted structure matches; and the interface metrics have no shared direction to take a best in anyway - `interface_dG` is better lower, `interface_dSASA` and `interface_sc` better higher. `<tool>_selected_batch` and `<tool>_selected_model` record which sample each design's structural columns came from - both, because an engine handed a list of seeds returns every sample from one batch. `min|mean|max|first` still apply one statistic to every structural column.
- `--fold_seed_list` (default `true`): run `--n_predictions` as one invocation carrying every seed, for the engines that take a seed list and keep each seed's outputs apart. The alternative, one process per seed, loads the model that many times, and on a small complex the load is most of the wall time - ESMFold2-Fast measured 1m 8s per task on a GB10 for a two-chain complex, nearly all of it startup. Applies to `esmfold2`, `esmfold2_fast` (`bin/fold/run_esmfold2.py` now loops `fold()` over `--seed` with the model resident), `openfold3` (its runner YAML's `experiment_settings.seeds` is already a list) and `protenix` (`runner/inference.py` loops `for seed in seeds:`). AF3 has the same ability under its own parameter, where a comma list in `--af3_seeds` already means "these seeds, one job". Boltz and RF3 are excluded because they are single-seed per process: Boltz calls `seed_everything(seed)` once, and RF3's inference engine config has `seed:` as a scalar. Set `--fold_seed_list false` to go back to one process per seed.
- GPU provenance trace. Every GPU task now records the device it ran on to `<outdir>/logs/gpu_trace_<datestamp>.txt`: timestamp, task hash, process, hostname, `n_gpus`, and the GPU index, UUID, model, driver version and total memory. New parameters: `--gpu_trace_dir`, `--gpu_trace_file`.

### Changed
- Supported Nextflow range is `!>=23.04.0, <27`, tested on 26.10.7.
- The MSA subsample seed is the Java string hash of the id and depth, so it stays the same across Nextflow versions. A resume from before this change re-runs the subsample tasks once.
- `conf/platforms/monash_containers.config` points every `nf-binder-design-utils` process at `0.1.8` on the Monash mirror. They were pinned at `0.1.6` and `0.1.5`, which predate the `peppr` dependency the refold's DockQ scoring needs, so a refold on M3 failed at the comparison step.
- The column order of `refold_sample_scores.tsv` and `refold_scores.tsv` is stable between runs. The RMSD tables were collected in arrival order, so which of the monomer and complex comparison blocks came first depended on which task finished first, and two runs over the same data could publish the same columns in a different order.
- `--rf3_alignment` is renamed to `--rf3_target_msa`, and a run that sets the old name stops with the new one named. Every MSA parameter in the pipeline now says "msa" - `--target_msa`, `--create_target_msa`, `--create_binder_msa`, `--use_msa_server`, `--msa_method`, `--msa_subsample`, `--protenix_use_msa`, `--af3_paired_msa`, `--rf3_create_target_msa` - with no `*_alignment` spelling left for an external MSA file. The design-time RF3 MSA keeps its `--rf3_` engine prefix, which is what distinguishes it from the refold's `--target_msa`.
- Refold scoring is available in every design workflow, not just `--method rfd4_proteina`. `--method rfd`, `rfd_partial`, `rfd3`, `bindcraft` and `germinal` all take `--refold_with` and run the same `REFOLD` subworkflow, giving the same engine-prefixed columns in their own `combined_scores.tsv`. Refolding is a held-out second opinion rather than a replacement for each workflow's own cofold: rfd and rfd_partial still run AF2 initial guess, rfd3 still runs RF3, and BindCraft and Germinal still run their own AF2 passes. That first cofold's scores are what the refold selects on, and refolding happens afterwards, on the designs worth the GPU time. The Boltz-only paths it replaces are gone: `BOLTZ_REFOLD_CORE`, `BOLTZ_REFOLD_SCORING`, `BOLTZ_REFOLD_SCORING_RFD3`, `BOLTZ_COMPARE_COMPLEX` and `BOLTZ_COMPARE_BINDER_MONOMER`. In `--method rfd` and `rfd_partial` the AF2 initial guess scoring that always ran (`BINDCRAFT_SCORING` plus `COMBINE_SCORES`) is unchanged and still produces `combined_scores.tsv` when no refold engine is named; it is now the `AF2IG_SCORING` subworkflow.
- Which designs are refolded is chosen explicitly, by three parameters that compose, and every design that reached the step is accounted for in `<refold_publish_dir>/refold_selection.tsv` with its verdict, rank and sort value. `--refold_filter` is a threshold gate on the first cofold's scores, in the same semicolon-separated syntax as `--rfd_filters` (`--refold_filter 'ipsae>=0.5;pae_interaction<=10'`); it is decided per design, so refolding starts while the rest of the set is still being scored. `--refold_sort_by` ranks by one metric, with a `-` prefix for descending; on its own it selects nothing, since without a cap every design that passes the gate is refolded anyway. `--refold_max` caps how many go through: the best N with `--refold_sort_by`, the first N to be scored without it. A cap does not stream, with or without a ranking - the best N needs the last design scored, and the first N needs a count kept across every design. Write the descending form with an `=` (`--refold_sort_by='-ipsae'`), or Nextflow reads the leading `-` as one of its own options. A filter naming a metric the score table does not have stops the run and lists the columns that are there, rather than silently rejecting every design.
- **Behaviour change for `--method rfd3`:** `--refold_max` no longer implies a ranking. `--full_refold_filter_sort` defaulted to `pair_pae_min`, so a capped refold took the best designs by that metric; its replacement `--refold_sort_by` defaults to unset, so a cap alone now takes the first N to finish, in whatever order that is. The run warns when `--refold_max` is set without `--refold_sort_by`. Add `--refold_sort_by='pair_pae_min'` to keep the old selection.
- Every refold parameter is spelled `--refold_*`. The `--full_refold_*` family is renamed without exception: `--full_refold_with` → `--refold_with`, `--full_refold_max` → `--refold_max`, `--full_refold_rf3_batch_size` → `--refold_rf3_batch_size`, and so on. `--full_refold_filter_sort` becomes `--refold_sort_by`. In `--method rfd` and `rfd_partial`, `--refold_af2ig_filters` becomes `--refold_filter`, which does the same thing in every workflow; the old name still works and warns.
- The refold's shared defaults move out of the workflow scripts into `conf/refold.config` (the `--refold_*` knobs, included for every entrypoint) and `conf/refold_fold_stack.config` (the fold stack a refold drives: `--n_predictions`, `--msa_method`, the `--af2_*`, `--protenix_*` and per-engine `--refold_<engine>_*` families, EnGens and FoldSeek). The second is included for the design workflows only: `--method fold` and `--method fold_pulldown` declare several of the same names with different values, and a config declaration beats a workflow script's default. Each workflow still declares its own `--refold_publish_dir` and `--fold_publish_dir`, which name a different directory in each.
- `--method rfd3`'s `combined_scores.tsv` carries the refold's engine-prefixed columns in place of the four Boltz-specific tables (`boltz_complex_*`, `boltz_monomer_*`, `boltz_target_aligned_binder_*`, `boltz_monomer_vs_complex_*`). `--method rfd` and `rfd_partial` likewise merge one refold table rather than three Boltz ones. rfd3 now writes `binders.fasta` with `--refold_fasta_score_columns` in the headers, as `--method rfd4_proteina` does.
- `--boltz_refold_batch_size` is removed. It batched several designs into one Boltz refold comparison task, and that Boltz-specific path no longer exists; the refold folds through the shared fold stack, where `--refold_boltz_batch_size` is samples per job.
- `--refold_binder_chain` / `--refold_target_chain` name the binder and target chains for the refold where the workflow has no derivation of its own, which is `--method bindcraft` and `--method germinal` (default binder `B`, target `A`). rfd3 and rfd4_proteina still derive them from the contigs, and rfd / rfd_partial know them from how AF2 initial guess writes its complexes.
- Refold scoring is no longer Boltz-specific. `BOLTZ_COMPARE_COMPLEX` folded the complex and measured it against the design inside one process, which tied the metrics to one engine; folding, comparison and interface scoring are now separate steps that work from structures, so any engine's predictions go through the same scoring. `--refold_oracles`, which existed because the Boltz path could not take another engine, is deprecated and folded into `--refold_with`. Removed with it: `--refold_create_target_msa`, `--refold_use_msa_server`, `--refold_alignment` and `--refold_target_templates` - the refold takes its MSA and template choices from the fold stack (`--create_target_msa`, `--target_msa`, `--use_msa_server`, `--msa_method`, `--templates`), and a run that sets one of the old names stops with the replacement named. `--refold_target_fasta` keeps its name and its meaning (see Added). Column names change for `--method rfd4_proteina`: `boltz_complex_plddt` becomes `boltz_plddt_max`, while the RMSD columns keep their names. `boltz_complex_pair_pae_min` has no replacement: the engine-independent metric in its place is `<tool>_pae_mean`, the mean of the full PAE matrix. The refolded structures move from `<outdir>/boltz_refold/` to `<outdir>/rfd4_proteina/refold/`.
- The refold in `--method rfd4_proteina` now runs 5 structures per design per engine rather than 1, as 5 fold jobs of one sample each with seeds 42, 43, ... rather than one job of 5 samples. The engines that batch samples share a single trunk and recycling pass across them, so five samples from one seed differ only in the diffusion noise while five seeds re-run the whole prediction; the disadvantage is five model loads rather than one, roughly 45 s of fixed cost each for Boltz on a GB10. The split comes from per-engine batch sizes of 1, declared as `--refold_<engine>_batch_size` for the engines whose plain name `nextflow.config` already declares (`boltz`, `esmfold2`, `chai1`, `openfold3`, `af3`, and `rf3` as before) and as `--protenix_batch_size` for Protenix, which this workflow declares itself. Setting one higher gives that engine a mixture: `--n_predictions 6 --refold_boltz_batch_size 3` is 2 seeds x 3 samples. `--method fold` and `--method fold_pulldown` are unchanged. The refold's long tables and the interface-score PDB names gain the fold batch (`<design>__<tool>__b<batch>.pdb`), because every job writes its single sample under the same model index and the batch is what tells two seeds' samples apart.
- RF3's engine flags are `--refold_rf3_*` in `--method rfd4_proteina` (`ckpt_path`, `num_steps`, `n_recycles`, `batch_size`, `early_stopping_plddt_threshold`, `seed`). The plain `--rf3_*` names belong to the design-time RF3 step in `--method rfd3`, where `--rf3_batch_size` means MPNN designs per RF3 task rather than samples per fold job, and a workflow's parameters are one flat namespace. Where a workflow declares the prefixed names the fold stack reads only those (`modules/local/fold/common/fold_params.nf`), so a design-time value cannot leak into the refold. `--method fold` and `--method fold_pulldown`, which have no design-time RF3 step, keep the plain names.
- `--protenix_seeds` takes a comma list again. It was a hard error because Protenix separates its seeds by directory (`<name>/seed_<N>/predictions/`) and not in the file name, so several seeds in one job collided in the flat `fold/predictions/` gather and mis-paired their confidence files. `PROTENIX_FOLD` now reads the seed back out of the path and puts it into the names it publishes and scores (`foldNamingProtenixSeedBit`), which is what makes a seed list usable.
- Every structure predictor in `--method fold` / `fold_pulldown` (`af2`, `af3`, `boltz`, `esmfold2`, `openfold3`, `protenix`, `rf3`) now honours `task.ext.args`, so extra engine CLI arguments can be set from config without a pipeline parameter for each option. `ALPHAFOLD2` was the only one that did not.
- `bin/foldseek/extract_design_chain.py` takes `--last-chains N` to keep the last N chains instead of guessing the binder as the chain with fewest atoms, which picks the wrong chain for a multi-chain binder or a target smaller than its binder.
- ColabFold MSAs are published as `{sequence_id}.a3m` (e.g. `PDL1.a3m`) rather than `{fasta_stem}.N.a3m` under a `result/` folder.
- The pipeline parses under Nextflow's strict syntax (the v2 parser), so it runs on current Nextflow without `NXF_SYNTAX_PARSER=v1`, while still supporting 24.04.3. The `lib/` Groovy classes become Nextflow functions in `modules/local/fold/common/`, named `foldParamsEngine`, `foldNamingSampleLabel` and so on in place of `FoldParams.engine` and `FoldNaming.sampleLabel`. `main.nf` includes every method's workflow rather than only the selected one, which adds a few seconds to startup since all ten are parsed on every run; `--method` still picks the one that runs, and each workflow's own parameter defaults stay private to it. In the platform configs, top-level `def` variables and helper functions become params or inline closures. Every method runs on 24.04.3, 24.10.0, 25.04.7 and 26.04.4, and the `examples/*/run-m3*.sh` scripts no longer export `NXF_SYNTAX_PARSER=v1`. Lint with `NXF_VER=25.04.7 nextflow lint -o concise main.nf workflows subworkflows modules nextflow.config conf tests`.

### Removed

- `bin/find_available_gpu.py` and the `--gpu_allocation_detect_process_regex` / `--germinal_gpu_allocation_detect_process_regex` parameters. The script's GPU-busy detection never worked inside Apptainer containers - Set `--gpu_devices` to enable the lock-based allocator instead.

### Fixed
- BindCraft2 tasks that segfault (139) or abort (134) while JAX/CUDA is tearing down, after the campaign has already finished and written its summary, are kept. The same status before `campaign done:`, or any other non-zero status, still fails the task.
- Boltz-2 fold and fold_pulldown of a homodimer failed with `All proteins with the same sequence must share the same MSA!`. Identical chains now share one MSA: the first chain's file, or one server MSA when that is what any copy would have used.
- BindCraft2 on the Monash M3 configs (`m3`, `m3_bdi`) disables JAX GPU command buffers, which crashed the task intermittently.
- `rf3` fold specs declare `chain_type: polypeptide(L)` for every sequence component. Without it, atomworks infers the chain type from the alphabet, so a low-complexity binder whose letters are all valid nucleotide codes - poly-alanine from a degenerate ProteinMPNN pass is the realistic case - was folded as RNA, and every comparison metric for that design came back `NaN`. The stack is protein-only, so the declaration is unconditional.
- From Nextflow 26, a `publishDir` `path:` or `pattern:` written as a plain string could not see the process's own inputs, so every method died at startup with `No such variable: step` / `meta` / `batch_id` before any task ran. The 18 such directives across 15 modules are closures now, which defers them to the task. This was independent of the strict syntax, and 24.04.3 was never affected.
- `SILENT_FROM_PDBS` referred to `${PATH}` unescaped in an interpolated script block, so `--method rfd` died with `No such variable: PATH` before any silent file was written.
- `FOLDSEEK_REMOTE_SEARCH` passed `$d` unescaped to `jq`, so Nextflow tried to interpolate it instead of leaving it as the jq variable the query needs.
- `PREPARE_RF3_TEMPLATE` and `RENAME_RF3_TEMPLATE_CHAINS` had their `publishDir` directives inside the `output:` block, where they are not directives at all, so their templates were never published.
- An unset `--refold_with` stopped the run with `unknown --methods entry ''` instead of skipping the refold.
- BoltzGen input staging no longer replaces an absolute entity path with a symlink to itself when that file is already the staged input.
- Every design workflow failed to compile under Nextflow 24.04.x and 24.10.0 with `Variable `log` already defined in the process scope`, although those releases are inside the supported range. The refold work reintroduced the pattern commit 6020de1 removed: inside a workflow body, an assignment whose right-hand side touches a script binding (`params`, `log`, `Channel`, or another workflow-scope variable) cannot be declared with `def` under the pre-25 parser. The `def`s are dropped from those assignments in `workflows/{rfd,rfd_partial,rfd3,rfd4_proteina,bindcraft,germinal}.nf` and `subworkflows/local/refold.nf`; `foldValidationValidate` (then `FoldValidation.validate`) is unpacked by index rather than by destructuring, which the old parser rejects for the same reason. Every method now compiles on 24.04.3, 24.10.0, 25.04.7 and 26.04.4. `tests/pipeline/compilation.nf.test` gains `germinal`, `rfd4_proteina` and a refold-enabled `rfd` case, since the two workflows the regression reached had no compilation test at all.
- `boltz_pae_mean` was always blank while every other engine filled `<tool>_pae_mean`. Boltz's confidence JSON carries no PAE of any kind, but it does write the full matrix as `pae_*.npz`, already read for ipSAE; `bin/parse_boltz_confidence.py --pae-npz` now takes the mean off it in the same step, so the column is filled from the same numbers ipSAE is computed from.
- BindCraft reporting failed to render against matplotlib 3.11. `Axes.boxplot`'s `labels` keyword became `tick_labels` in 3.9 and is gone in 3.11, and the report has to run against whatever matplotlib the BindCraft image carries; it now picks the keyword from the signature once and uses it for all thirteen boxplots.
- Two fold runs in one workflow wrote their per-engine score tables to the same path, so the second overwrote the first and the merge downstream saw rows for complexes it never folded. The fold stack now takes a publish label (`FOLD`, `FOLD_PREDICT` and each engine subworkflow), which the refold uses to keep the complex folds and the binder-monomer folds apart.
- `bin/rmsd4all.py` compared multi-chain structures in file order rather than in the order the `--superimpose-chains` / `--score-chains` lists gave, and `rmsd_all` pairs atoms by position. Two complexes holding the same chains but written in the opposite order - an RFD4-Proteina design, which writes the binder first, against a refold that writes the target first - had the binder measured against the target: 21 Å where the structures agree to 1.3 Å. The chains are now taken in the order asked for, which is what makes the two lists a statement of correspondence.
- BindCraft interface scoring of a Boltz-refolded complex was given the design's binder chain id, but the refolded complex has its own chain ids (binder A, target B). Wherever the design's binder was not chain A - `--method rfd4_proteina`, where it is B - every interface metric, and the `sequence` column beside them, described the target rather than the binder.
- rfd4_proteina: `--rfd4_target_chain` / `--rfd4_binder_chain` resolved to the literal string `"false"` when left unset, because the params default to boolean `false` and `false.toString()` is a non-empty, therefore truthy, string. The A/B default and the derivation from `--contigs` never ran, so filter metrics were computed on a chain that does not exist - every `rg` blank and every design rejected - and the binder sequence was read from the wrong chain.
- rfd4_proteina: the `boltz_monomer_vs_complex_rmsd_*` columns in `combined_scores.tsv` were always empty. The merge stripped `_model_0.pdb` / `_monomer` from the RMSD table's `structure1`, but the values there end in `_complex.pdb`, so the key never matched a design id.
- `--boltz_num_workers` (default: `task.cpus`, unchanged): Boltz's dataloader workers deadlock on some platforms, leaving the run at 0% GPU indefinitely rather than failing. `conf/platforms/arm64.config` sets it to 0. Previously `--num_workers` was hardcoded to `task.cpus` in three modules and could not be overridden, since a duplicate flag in `ext.args` does not win.
- rfd4_proteina: `COMBINE_RFD4_SCORES` failed with `Not a valid path value type` whenever the filters rejected every design, because the empty-channel fallback passed `Channel.of(file(...))` to `ifEmpty`, which takes a value rather than a channel.
- RF3 wrote its caches to `$HOME`, which is `/` when the container runs as a uid with no passwd entry - what `conf/platforms/arm64.config` asks for under Docker so a task can write its own work directory. `rf3 fold` died with `PermissionError: [Errno 13] Permission denied: '/.cache'` before any folding. `RF3_FOLD` and `ROSETTAFOLD3` now set `XDG_CACHE_HOME`, `XDG_CONFIG_HOME` and `TRITON_CACHE_DIR` inside the task directory, as the Boltz module already did.
- rfd3: treat unset/`false` `--rf3_batch_size` as 1 (avoids Boolean→Integer cast failure when a shared config sentinel is present).
- The GPU lock (`--gpu_devices`) failed whenever the tasks sharing it did not all run as the same user. Some images run as root and others are pinned to the invoking user (`conf/platforms/arm64.config` does this under Docker), and the lock files take the ownership of whichever task created them, so a task running as anyone else could not open one for writing and waited out `--gpu_lock_timeout` before failing. `bin/gpu_lock.sh` now creates the lock directory and its files world-writable, and a lock file it cannot write is reported once and fails the task immediately rather than being waited on. The GPU trace directory is created the same way; a trace row written by a task running as another user was previously dropped in silence. A lock directory left behind by an earlier run has to be deleted for the new permissions to take effect.
- `examples/pdl1-rfd/run-m3-full.sh` and `examples/pdl1-bindcraft/run-m3.sh`: point at repo `main.nf`, pin `NXF_VER=24.10.0`, and drop mid-command `#` comments that broke the Nextflow invocation.
- Root `nextflow.config` report/trace timestamps use `params.trace_timestamp` instead of a top-level `def`, so Nextflow >=26 can parse the root config.
- Remove unused `random_choice` helper from `conf/platforms/m3.config`.
- Quarto reports: set writable `XDG_*` / Jupyter runtime dirs so rendering works in Apptainer (was failing with `Could create runtime directory for jupyter transport`).
- Local multi-GPU runs no longer stack tasks on one card while another sits idle ([#14](https://github.com/Australian-Protein-Design-Initiative/nf-binder-design/issues/14)).
- docs workflow: `main`, `develop` and tag pushes no longer race each other deploying to `gh-pages`. A release triggered all three at once and two failed with `cannot lock ref 'refs/heads/gh-pages'`, so the versioned docs were never published. Runs are now serialised and a rejected push is retried.
